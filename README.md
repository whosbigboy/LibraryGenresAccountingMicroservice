# Library Genres Accounting Microservice

Учебный проект для учета жанров и книг в библиотеке. Приложение разделено на
несколько Spring Boot-микросервисов, которые запускаются вместе через Docker
Compose и используют общую PostgreSQL-базу данных.

## Архитектура контейнеров

Общий файл запуска находится в корне проекта:

```text
docker-compose.yml
```

Он описывает четыре контейнера:

| Контейнер | Назначение | Порт хоста |
| --- | --- | ---: |
| `database` | PostgreSQL 16, хранение жанров и книг | 5432 внутри сети |
| `genres` | CRUD-сервис жанров | 8080 |
| `books` | CRUD-сервис книг | 8081 |
| `reports` | Формирование Excel, PDF и Word-отчетов | 8082 |

Структура исходного кода:

```text
lab4/
└── library_genres_registration/

lab5/
├── book_registration/
├── reports_registration/
└── database/
```

### Контейнер базы данных

Используется образ `postgres:16-alpine`. В Compose задаются:

```text
POSTGRES_DB=library
POSTGRES_USER=library
POSTGRES_PASSWORD=library
```

Данные подключены к именованному volume `postgres-data`, поэтому пересоздание
контейнера базы не удаляет данные. Удаление данных происходит только при
использовании:

```powershell
docker compose down -v
```

Healthcheck базы выполняется через `pg_isready`. Сервисы жанров и книг начинают
запуск после готовности PostgreSQL.

### Контейнеры микросервисов

Каждый Java-сервис собирается собственным многоэтапным Dockerfile:

1. Maven-этап компилирует проект и создает JAR-файл.
2. Runtime-этап на `eclipse-temurin:17-jre-alpine` запускает только JAR-файл.

Так Maven и исходные файлы не попадают в конечный runtime-образ.

Запуск всех контейнеров:

```powershell
docker compose up --build
```

Запуск в фоне:

```powershell
docker compose up -d --build
```

Проверка состояния:

```powershell
docker compose ps
```

Остановка без удаления данных базы:

```powershell
docker compose down
```

## Связь между микросервисами

Контейнеры используют имена сервисов Docker Compose как DNS-имена:

```text
books   -> http://genres:8080
reports -> http://books:8081
reports -> http://genres:8080
```

Сервис книг не хранит копию жанра. Он сохраняет `genreId`, а существование
жанра проверяет HTTP-запросом к сервису жанров. Сервис отчетов получает книги и
жанры через HTTP, объединяет их данные и формирует документы.

Снаружи компьютера доступны:

- жанры: <http://localhost:8080>;
- книги: <http://localhost:8081>;
- отчеты: <http://localhost:8082>.

## Сервис жанров

Исходный код находится в
[lab4/library_genres_registration](./lab4/library_genres_registration).

### Модель `Genre`

Жанр содержит:

```json
{
  "id": 1,
  "name": "Фантастика",
  "description": "Научная фантастика и космические приключения"
}
```

`id` генерируется PostgreSQL автоматически. Начальные жанры создаются при
старте, если в таблице еще нет записи с таким названием:

- Фантастика;
- Фэнтези;
- Детектив;
- Роман;
- История;
- Научно-популярная литература.

### Методы API

| Метод | URL | Назначение | Успешный ответ |
| --- | --- | --- | --- |
| `GET` | `/genres` | Получить все жанры | `200 OK` |
| `GET` | `/genres/{id}` | Получить жанр по ID | `200 OK` или `404 Not Found` |
| `POST` | `/genres` | Создать жанр | `201 Created` |
| `PUT` | `/genres/{id}` | Изменить название и описание | `200 OK` или `404 Not Found` |
| `DELETE` | `/genres/{id}` | Удалить жанр | `204 No Content` или `404 Not Found` |

Пример тела для `POST` и `PUT`:

```json
{
  "name": "Биография",
  "description": "Истории жизни известных людей"
}
```

Идентификатор в теле запроса указывать не нужно.

Swagger UI:

<http://localhost:8080/swagger-ui.html>

OpenAPI JSON:

<http://localhost:8080/v3/api-docs>

## Сервис книг

Исходный код находится в
[lab5/book_registration](./lab5/book_registration).

### Модель `Book`

Книга содержит:

```json
{
  "id": 1,
  "title": "Путешествие к звездам",
  "description": "История космической экспедиции.",
  "cost": 0,
  "genreId": 1
}
```

- `id` генерируется базой;
- `title` — название книги;
- `description` — описание;
- `cost` — стоимость;
- `genreId` — идентификатор жанра из сервиса жанров.

Книга считается бесплатной, если `cost` равен `0` или `null`.

### Методы API

| Метод | URL | Назначение | Успешный ответ |
| --- | --- | --- | --- |
| `GET` | `/books` | Получить все книги | `200 OK` |
| `GET` | `/books/{id}` | Получить книгу по ID | `200 OK` или `404 Not Found` |
| `POST` | `/books` | Создать книгу | `201 Created` |
| `PUT` | `/books/{id}` | Изменить книгу | `200 OK` или `404 Not Found` |
| `DELETE` | `/books/{id}` | Удалить книгу | `204 No Content` или `404 Not Found` |
| `GET` | `/books/{id}/genre` | Получить жанр книги через HTTP | `200 OK` |

Пример тела для создания или изменения:

```json
{
  "title": "Новая книга",
  "description": "Описание книги",
  "cost": null,
  "genreId": 1
}
```

При создании и изменении `genreId` проверяется запросом к сервису жанров.

Swagger UI:

<http://localhost:8081/swagger-ui.html>

## Сервис отчетов

Исходный код находится в
[lab5/reports_registration](./lab5/reports_registration).

Сервис не хранит собственную таблицу. Он получает данные у сервисов книг и
жанров через `RestClient`.

| Метод | URL | Результат |
| --- | --- | --- |
| `GET` | `/reports/free-books.xlsx` | Excel со списком бесплатных книг |
| `GET` | `/reports/free-books.pdf` | PDF с круговой диаграммой бесплатных книг по жанрам |
| `GET` | `/reports/books.docx` | Word-таблица со всеми книгами |

В Excel используются столбцы `Название` и `Описание`.

В Word используются столбцы:

```text
ID | Название | Жанр | Стоимость
```

Для книги с нулевой или пустой стоимостью выводится слово `бесплатная`.

Ссылки для скачивания:

- <http://localhost:8082/reports/free-books.xlsx>
- <http://localhost:8082/reports/free-books.pdf>
- <http://localhost:8082/reports/books.docx>

## Используемые библиотеки и технологии

### Общие технологии

- Java 17;
- Spring Boot 4.1.0;
- Spring MVC (`spring-boot-starter-webmvc`) для REST-контроллеров;
- Spring Data JPA (`spring-boot-starter-data-jpa`) для работы с сущностями и
  репозиториями;
- Hibernate как JPA-провайдер;
- PostgreSQL JDBC Driver для подключения к PostgreSQL;
- Docker и Docker Compose для упаковки и запуска;
- Maven для сборки.

### Документация API

`springdoc-openapi-starter-webmvc-ui` автоматически создает OpenAPI-описание и
Swagger UI для сервисов жанров и книг.

### Генерация документов

- Apache POI `poi-ooxml` — создание `.xlsx` и `.docx`;
- OpenPDF — создание PDF;
- JFreeChart — построение круговой диаграммы;
- H2 — тестовая база данных для тестов сервиса жанров и не используется как
  production-база.

## Как в проекте используется компонентно ориентированное
программирование (КОП)

Компонентно ориентированное программирование рассматривает приложение как
набор относительно самостоятельных компонентов с понятными интерфейсами.
Компонент скрывает внутреннюю реализацию и предоставляет другим компонентам
только необходимый контракт.

В этом проекте компонентами являются:

1. компонент базы данных;
2. компонент регистрации жанров;
3. компонент регистрации книг;
4. компонент формирования отчетов.

Каждый микросервис можно разрабатывать, собирать и запускать отдельно, но
вместе они образуют библиотечную систему.

### Разделение ответственности

Внутри сервиса жанров роли разделены:

- `GenreController` принимает HTTP-запросы;
- `GenreRequest` описывает входные данные без изменяемого `id`;
- `GenreService` содержит бизнес-операции;
- `GenreRepository` отвечает за доступ к данным;
- `Genre` представляет сущность базы данных.

Аналогично устроен сервис книг:

- `BookController` — REST-интерфейс;
- `BookRequest` — входной контракт;
- `BookService` — правила создания, изменения и удаления;
- `BookRepository` — persistence-компонент;
- `GenreClient` — компонент межсервисного взаимодействия;
- `Book` — JPA-сущность.

В сервисе отчетов:

- `ReportController` — HTTP-точки скачивания документов;
- `ReportService` — получение данных и преобразование их в файлы;
- `RestClient` — компонент доступа к сервисам книг и жанров;
- Apache POI, OpenPDF и JFreeChart — специализированные компоненты генерации.

### Инкапсуляция

Внутренние детали компонентов скрыты:

- контроллер не работает с SQL напрямую;
- сервис книг не знает внутреннее устройство базы жанров;
- отчетный сервис не обращается к таблицам напрямую и использует API;
- репозитории скрывают операции JPA;
- генерация конкретного формата скрыта внутри `ReportService`.

Клиент взаимодействует с компонентом только через REST-контракт:
URL, HTTP-метод, JSON и код ответа.

### Интерфейсы и контракты

REST endpoint выступает интерфейсом между компонентами. Например, сервис книг
использует контракт жанров:

```text
GET http://genres:8080/genres/{id}
```

Сервис отчетов использует контракты:

```text
GET http://books:8081/books
GET http://genres:8080/genres
```

Это уменьшает связанность: отчетам не нужно знать структуру Java-классов
сервиса книг или SQL-схему PostgreSQL.

### Композиция компонентов

Система строится композицией компонентов:

```text
PostgreSQL
    ↑
Genres Service ← Book Service
    ↑              ↑
    └── Reports Service ──┘
```

`Book Service` компонуется с `GenreClient`, а `Reports Service` — с HTTP-
клиентами книг и жанров и библиотеками генерации документов.

### Независимое развертывание и замена

Каждый сервис имеет собственные:

- исходные файлы;
- `pom.xml`;
- Dockerfile;
- порт;
- настройки окружения.

Поэтому реализацию компонента можно заменить без переписывания всех остальных
частей, если сохранить REST-контракт. Например, PostgreSQL можно оставить
неизменным, а внутреннюю реализацию отчетов заменить при сохранении трех
endpoint-ов отчетов.

### Преимущества КОП в этом проекте

- локализация изменений внутри одного сервиса;
- повторное использование Spring-компонентов;
- понятное разделение бизнес-логики и инфраструктуры;
- независимая сборка и тестирование;
- возможность масштабировать сервисы отдельно;
- слабая связанность через HTTP-контракты;
- изоляция форматов отчетов от CRUD-логики.

### Особенности и ограничения КОП здесь

Компонентный подход требует явно поддерживать контракты. Если изменить URL или
формат JSON сервиса жанров, необходимо обновить `GenreClient` и отчетный сервис.
Также HTTP-связь создает сетевые ошибки и зависимость от доступности соседних
контейнеров. Поэтому Compose задает `depends_on`, а каждый сервис должен
учитывать, что другой сервис может временно быть недоступен.

Общая база упрощает учебную систему, но создает более тесную связь на уровне
хранения данных. Основное компонентное разделение при этом сохраняется на
уровне API и ответственности сервисов: сервис книг не выполняет SQL-запросы к
таблице жанров, а использует HTTP-интерфейс сервиса жанров.

## Сборка без Docker

Для сервиса жанров:

```powershell
cd lab4/library_genres_registration
.\mvnw.cmd clean test
```

Для сервиса книг:

```powershell
cd lab5/book_registration
mvn clean package
```

Для сервиса отчетов:

```powershell
cd lab5/reports_registration
mvn clean package
```

Для полноценного запуска с PostgreSQL рекомендуется использовать Docker Compose.
